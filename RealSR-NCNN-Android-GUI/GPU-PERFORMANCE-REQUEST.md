# Opt-in Android 16 GPU performance request

Video settings have one persisted, default-off checkbox: **Request higher GPU performance (Android 16+)**. The job snapshots its value. It is selectable on Android >=36 with the actual GPU backend, independently of runtime hint capability. CPU selection and Android <36 disable the control without clearing its saved checked preference. Both explicit Vulkan neural inference and OpenGL shader enhancement can request a worker-owned session. Existing CPU ADPF and worker priority remain independent. No Game Mode, GameState, game classification, Game Turbo links, settings intents, root, thermal overrides, dummy load or CPU-as-GPU fallback.

## Public stable API / compatibility

The ABI was checked against the shipping **android-16.0.0_r1** stable NDK header, not AOSP main or private headers:
https://android.googlesource.com/platform/frameworks/native/+/android-16.0.0_r1/include/android/performance_hint.h

`native-video/android36-performance_hint.reference.h` is that official Apache-2.0 reference. `gpu_hint_abi_test.cpp` statically checks all resolved function signatures against it. r28c predates these declarations; the production helper declares only frozen opaque structs, the frozen feature enum and function-pointer signatures. All performance-hint symbols are resolved from libandroid with dlopen/dlsym **after** a native API36 check. No API36 hint symbol is an ELF link-time dependency; minimum Android API24 remains usable. Java does not load/probe the GPU helper on older OS versions. No SDK upgrade is needed for these native APIs.

`APerformanceHint_isFeatureSupported` is public API36. Check `APERF_HINT_SESSIONS=0` and `APERF_HINT_GRAPHICS_PIPELINE=3`, plus manager/symbol/session availability. The stable release has **no separate feature enum for GPU notify-hint support**. Public reset/increase documentation says unsupported hints can be silently dropped. Therefore successful submission is never described as confirmed GPU boost support, maximum frequency, or measured performance gain.

## Session and measured timing

At job time the worker independently probes session feature 0, graphics feature 3, manager and exports. It uses graphics mode only when feature 3 and its optional exports are present. Otherwise it creates an ordinary API33 session with manager, actual Linux TID and target, then uses the API36 GPU-only reset. Graphics creation rejection (including EBUSY with a returned session) closes the rejected session and attempts ordinary creation exactly once; no retry loop. Ordinary sessions set no graphics mode and perform no ongoing duration reports, target updates or extra glFinish. Their only hint is the once-per-job reset; shutdown closes that same job session. The worker owns its session bound to its real Linux TID. It sends **one** `APerformanceHint_notifyWorkloadReset(session, false, true, "RealSR video start")` immediately before pipeline frame production starts. This fixed-model/fixed-resolution job has no legitimate recurring workload increase, so it does not issue increase pulses or spam reset per frame.

For a successfully created graphics session only, each produced output reports the actual CLOCK_MONOTONIC-compatible wall duration from decoded-frame acquisition through inference, bitmap upload and completed output drawing/submission. Opt-in drawing uses `glFinish` before submitting the encoder buffer, so asynchronous GPU completion is not mistaken for submission time. NCNN inference returns its completed bitmap and shader readback completes its offscreen work. This synchronization may itself affect throughput; compare on-device before choosing the option for long jobs. The legacy total-only public reporting API is used: Android internally classifies it as **CPU duration=total, GPU duration=0**. This is end-to-end graphics critical-path wall timing, **not measured GPU duration** and not a measured CPU/GPU split. No split is invented. Ordinary reset-only sessions never feed GPU-heavy wall time into this CPU-classified report. Target uses the existing explicit target or previous measured total in Auto mode. Original presentation timestamps, preview windows, bounded frame leases and continuous encoder drain remain unchanged.

Missing required ordinary symbols, no session feature/manager, failed ordinary creation, or reset/report failure disable only the hint session. The immutable Java probe tuple preserves exact missing export names, separately evaluated session/graphics features, manager absence and native load errors. JNI status/getters retain graphics creation, ordinary creation, reset, report and target-update errno; existing worker status shows these reasons and selected best-effort mode, not a new Game Mode UI. Optional graphics exports are not mandatory for ordinary creation. Video continues on the already selected inference backend. No fallback changes CPU/GPU selection. Hint acceptance is best effort and can be silently ignored by a phone. Android/OEM power policy and thermal limits still decide clocks.

## Verification / device acceptance

Host policy/wrapper tests cover opt-out, CPU/API eligibility without capability gating, one reset, measured total reporting, invalid durations, failure disabling and exactly-once close. Native tests cover public GPU-only reset arguments, config ownership, capability/manager failure, EBUSY cleanup, reporting and idempotent close. JUnit adapters include standalone Java regressions in normal Gradle tests; native GPU tests are in normal host CTest as well as the isolated target.

`VideoGpuHintsDeviceTest` covers persistence/job snapshot, old API and CPU guards, runtime support/session cleanup. `VideoPipelineTest.graphicsRequestUsesRealPipelineDrawingAndPreservesVfr` runs real codec/EGL drawing and VFR preservation with the graphics request; its identity processor is explicitly a codec-test seam, not NCNN or shader inference verification. These instrumentation cases are compile-checked, **not executed until an adb device is available**.

On a real ARM64 Android16 phone: run the instrumentation cases; run a short SDR AVC/AAC clip with explicit Vulkan 2x neural and then a shader model, option off/on; compare output pixels, frame count/PTS, audio sync and cancellation; confirm diagnostics remain best effort; record throughput/thermal behavior rather than claiming frequency from hint return codes. Repeat on unsupported Android16 hardware to verify the checkbox remains selectable and failure is diagnosed without changing inference; older Android and CPU selection keep it disabled. No accepted hint proves frequency lock or throughput improvement.
